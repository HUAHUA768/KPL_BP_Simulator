## 一、背景与目标

### 1.1 需求原文

| # | 需求 | 要点 |
|---|------|------|
| 1 | 五个分路的元流之子，A 队**本场比赛**只能选一个使用 | 一旦使用了元射，则其它四个元流都不能再选 |
| 2 | 基于第 1 点，若 A 队已使用元射，则 B 队**不用再 ban 其它四个元流**，但 B 队**依然可以进行元流五选一**，故而 A 队**依然有 ban 五个元流的权力** | ban 权与 pick 权解耦 |
| 3 | 前端交互与**当前已存在规则一致** | 元流不可 ban（或 pick 轮次不可 pick）时，头像**变灰** + 右上角**「限」字** |
| 4 | 有不确定的可以问；没有就制定方案并施工 | 本方案先落文档，再施工 |

### 1.2 需求方已确认的边界（本方案的事实前提）

> 以下 5 条经需求方逐条确认，是**规则语义的唯一依据**。施工时任何与此冲突的实现都是 bug。

| 决策点 | 结论 | 影响的实现点 |
|--------|------|-------------|
| **锁定范围** | **整场比赛累计**，不是单局 | 锁定状态必须跨局持久化并重算 |
| **ban 是否触发锁定** | **不算**。只有 `pick` 才触发「本场只能选一个」 | 判定输入只取历史 `pick` 记录 |
| **对手（B 队）这局还能否选元流** | **能**，从剩余四个中任选一个 | 锁是**按队伍**的，不是全局唯一资源 |
| **A 队已 pick 元射后，A 队还能 ban 其它四个吗** | **能**。ban 权完整保留（「A 队依然有 ban 五个元流的权力」） | A 方 `CanBan` 保持 `true` |
| **A 队已 pick 元射后，B 队还能 ban 其它四个吗** | ❌ **不能**（实测补充确认，见 §8.9）。需求原文「B 队**不用再 ban** 其它四个元流」是一条**对 B 的禁止规则**，不是对 A 的描述 | B 方 `CanBan` 置 `false` |
| **元射被 ban 掉后，A 队还能选其它四个吗** | **能**。被 ban 不产生锁定，仅该英雄本局不可用 | 判定只看「本队历史 pick」 |

> ⚠️ **第 5 条是实战测试后补充确认的，也是本方案初稿最大的语义误读**。
> 初稿把「B 队不用再 ban」理解成了"A 队的 ban 权不受影响"的**同义复述**，
> 因此只保护了 A 的 ban 权，却忘了剥夺 B 的 ban 权 —— 导致
> "AG 选了元射，狼队后续仍能 ban 元坦"。详见 §8.9。

## 二、规则的形式化定义（施工前必读）

### 2.1 术语

- **元流组**：五个英雄的集合。以**英雄名前缀**识别，而非硬编码 ID。

  | 英雄 | 分路 | 当前库 ID |
  |------|------|----------|
  | 元流之子·坦克 | 对抗路、打野 | 33 |
  | 元流之子·法师 | 中路 | 60 |
  | 元流之子·射手（元射） | 发育路 | 83 |
  | 元流之子·刺客 | 打野 | 105 |
  | 元流之子·辅助 | 游走 | 132 |

  取证命令（已实测执行，结果如上表）：
  ```bash
  source scripts/env.sh
  mysql -h"$DB_HOST" -P"$DB_PORT" -u"$DB_USER" -p"$DB_PASSWORD" kpl_bp \
    -e "SELECT id, name, is_active FROM hero WHERE name LIKE '元流%' ORDER BY id;"
  ```

- **usedYuanliu(team)**：该队在本场比赛**本局之前的各局中 `pick` 过的**元流英雄集合。
  ban 不计入。

  > ⚠️ **计算时机 —— 本方案初稿在此处判断错误，施工时已修正（详见 §8.1）**。
  >
  > **初稿（错误）**：认为"本局内的 pick 不可能改变本局的锁定结果，故只需在 `StartGame`
  > 计算一次，无需动态重算"。这个判断把"锁定的**输入**"（历史 pick 集合）与
  > "锁定的**生效时机**"混为一谈。
  >
  > **实际（正确）**：本规则必须分两条路径实现，缺一不可 ——
  >
  > | 路径 | 触发点 | 输入 | 实现位置 |
  > |------|--------|------|---------|
  > | **局内动态** | 本局某方 pick 元流的那一刻 | 本局的实时 pick | `Engine.lockExclusiveGroupFor`（pick 后立即收紧权限） |
  > | **跨局累计** | 每局开始时 | 本局之前全部历史局 | `GameService.collectYuanliuUsage` → 写入初始权限表 |
  >
  > 若只做第二条，会出现**"当局不锁、下局才锁"** —— 第 1 局 pick 元射后其余四个仍可 pick，
  > 直接违反需求 1「一旦使用了元射，则其它四个元流都不能再选」。

### 2.2 规则公式

对**本局**的每一支队伍 T 与每一个元流英雄 h，设 **opp(T)** 为对手方：

```
T 本局能否 pick h  ⇔  usedYuanliu(T) 为空  或  h ∈ usedYuanliu(T)
T 本局能否 ban  h  ⇔  usedYuanliu(opp(T)) 为空      ← 对手未用过时才能 ban
```

**⚠️ 第二条是初稿写错、实战后修正的地方**（初稿写作 `⇔ true`，见 §8.9）。

**ban 权的不对称性**（本规则最反直觉、也最容易实现错的一点）：

| 谁 | 对五个元流的 ban 权 | 依据 |
|----|-------------------|------|
| **用过元流的一方 A** | ✅ **保留** | 需求 2：「A 队依然有 ban 五个元流的权力」 |
| **对手 B** | ❌ **剥夺** | 需求 2：「B 队**不用再 ban** 其它四个元流」 |

> 语义解读：A 用过之后，其余四个元流对 B 已**没有 pick 威胁**（A 不可能再选），
> 因此 B "不必再 ban" —— 这里"不用"是**授权缺失**（不得），不是"可选但不必"。
> 而 A 自己的 ban 权是**防守手段**，不因己方已使用而剥夺。

等价的四种情形：

| 情形 | `usedYuanliu(T)` | 对该队效果 |
|------|------------------|-----------|
| **双方都未用过** | ∅ | 双方对五个元流**都可 ban、都可 pick**（完整的五选一） |
| **T 已 pick 过元射** | {元射} | **T 自己**：其余四个不可 pick，但**可 ban**；**对手**：不可 pick、也**不可 ban** |
| **对手已 pick 过元射** | ∅（但 opp 非空） | T：其余四个可 pick（五选一），但**不可 ban** |
| **从未用过，但五个都被 ban** | ∅ | 五个都不可 pick（ban 占用，非本规则），**规则上不锁定** |

### 2.3 ⚠️ 与既有全局BP记忆的叠加：这是本方案最容易出错的地方

元流规则**不是**在真空中生效的，它与已有规则**叠加**。以"A 队第 1 局 pick 了元射，第 2 局"为例：

| 英雄 | 元流规则 | 全局BP记忆 | **最终** |
|------|---------|-----------|---------|
| 元射（A 队自己选过） | pick❌ ban✅（A）／ban❌（B） | A：pick❌ ban✅；B：pick✅ ban❌ | A: `{ban:T,pick:F}`；B: `{ban:F,pick:T}` |
| 坦克/法师/刺客/辅助 | pick❌ ban✅（A）／ban❌（B） | 未触及（全 `true`） | A: `{ban:T,pick:F}`；B: `{ban:F,pick:T}` |

**结论**：叠加后，五个元流的权限形态**完全一致**（A 可 ban 不可选、B 可选不可 ban），
这正是需求 1 + 需求 2 的完整表达。

> 💡 需求 2 的两句话分别对应两个方向：
> 「A 队依然有 ban 五个元流的权力」→ **保护 A 的 ban**；
> 「B 队不用再 ban 其它四个元流」→ **剥夺 B 的 ban**。
> 初稿只做了前半句，漏了后半句（§8.9）。
>
> 前端正是靠这对不对称布尔渲染出不同表现：**对 B 灰化 + 「限」**；
> **对 A 不可 pick 但 ban 轮次仍彩色可点**。

### 2.4 前端渲染契约（复用既有机制，零新增 UI 概念）

需求 3 明确要求「与当前已存在的规则一致」。既有机制已经完备：

- 后端 `buildRoomState` 下发 `heroes[].permissions`（4 布尔，唯一事实来源 `engine.Permissions`）；
- 前端 `BanPickBoard.isBlockedByRule(heroId)` 按**当前方 + 当前动作**读对应布尔位；
- `isHeroActionable = 未被占用 && !isBlockedByRule` → 不可点击；
- `HeroCard` 的 `restricted` prop → **灰化（`grayscale brightness-50`）+ 禁用光标 + 居中「限」角标**。

因此 **§三 不需要改任何前端组件** —— 只要后端把权限位算对，界面行为自动正确。
唯一的边角是 §2.5 的「不可 pick 但可 ban」在 ban 轮次应当正常高亮。

### 2.5 一个必须显式验证的交互细节

`isBlockedByRule` 是**按当前动作类型**取布尔位的，因此同一个英雄在不同轮次表现不同：

| 轮次 | `isBlockedByRule` 读取 | 结果 | 期望 UI |
|------|----------------------|------|---------|
| **ban 轮次** | `!XCanBan` | `XCanBan=true` → `false` | **正常彩色、可点击**（A 队要能 ban 另外四个） |
| **pick 轮次** | `!XCanPick` | `XCanPick=false` → `true` | **灰化 + 「限」角标、不可点击** |

这正是需求 2 与需求 3 的交汇点，**验收时必须分轮次实测**（见 §四 4.4）。

### 3.1 【A1】新建 `internal/service/yuanliu.go` — 规则单一事实来源

**设计原则**：把「什么是元流」与「锁定规则」收敛到一个文件、一组纯函数，
避免名字前缀判断散落到 `game_service.go` / `room_handler.go` / 前端三处。

```go
package service

import "strings"

// YuanliuPrefix 元流之子的名字前缀。
// ⚠️ 用「名字前缀」而非硬编码 ID：英雄 ID 由 auto_increment 决定，
//    不同环境（seed 重建 / 新增迁移）可能不同；名字是业务事实。
const YuanliuPrefix = "元流之子"

// IsYuanliuHero 判断某英雄是否属于元流之子五选一组。
func IsYuanliuHero(name string) bool {
    return strings.HasPrefix(strings.TrimSpace(name), YuanliuPrefix)
}

// YuanliuGroupIDs 从英雄列表里筛出元流组的英雄 ID（顺序稳定，便于测试断言）。
// heroes 必须按 id 升序传入（heroRepo.ListActive 已保证）。
func YuanliuGroupIDs(heroes []*model.Hero) []int {
    ids := make([]int, 0, 5)
    for _, h := range heroes {
        if h.ID > 0 && IsYuanliuHero(h.Name) {
            ids = append(ids, h.ID)
        }
    }
    return ids
}

// YuanliuLocked 计算「本队因已使用过元流而不可再选」的英雄集合。
//
// 规则（见方案 §2.2）：
//   - usedByTeam 为空          → 返回空集（该队仍有完整的五选一权力）
//   - usedByTeam 非空（已用过） → 返回整组中**除已用过的那些之外**的全部 ID
//
// 注意：ban 不计入 usedByTeam（需求方确认），调用方只传 pick 记录。
func YuanliuLocked(groupIDs []int, usedByTeam map[int]bool) map[int]bool {
    locked := make(map[int]bool)
    if len(usedByTeam) == 0 {
        return locked
    }
    for _, id := range groupIDs {
        if !usedByTeam[id] {
            locked[id] = true
        }
    }
    return locked
}
```

**为什么 `usedByTeam` 非空就锁整组剩余部分**：需求 1 说「一旦使用了元射，则其它四个元流都不能再选」。
若某队历史 pick 过"坦克"，则其余四个（含元射）也应被锁。公式 `整组 - 已用过` 同时覆盖这两种情况。

### 3.2 【A2】改造 `game_service.go` — 派生元流锁定

#### 步骤 1：`StartGame` 里收集「本队历史已用元流」

现有 `StartGame` 只读**上一局**记录（`gameNumber-1`）。元流规则要求**整场比赛累计**，
因此必须遍历本场比赛的**全部历史局**（含已结束的任意一局）。

```go
func (s *GameService) StartGame(matchID, gameNumber, blueTeamID, redTeamID int) (*Engine, error) {
    heroes, err := s.heroRepo.ListActive()
    if err != nil {
        return nil, fmt.Errorf("加载英雄池失败: %w", err)
    }

    // 0. 元流组（问题：五选一锁定）—— 按名字前缀识别，不硬编码 ID
    yuanliuIDs := YuanliuGroupIDs(heroes)

    // 1. 基础权限表（不变）
    perms := make(map[int]*HeroPerm, len(heroes))
    for _, h := range heroes {
        if s.tournamentBanned[h.ID] {
            perms[h.ID] = NonePerm()
        } else {
            perms[h.ID] = FullPerm()
        }
    }

    // 2. 非第一局：全局BP记忆（既有规则，不变）
    if gameNumber > 1 {
        prevGame, err := s.gameRepo.GetGameByMatchAndNum(matchID, gameNumber-1)
        if err != nil {
            return nil, fmt.Errorf("读取上一局(%d局)失败: %w", gameNumber-1, err)
        }
        if prevGame != nil && prevGame.BPCompleted {
            actions, err := s.gameRepo.ListBPActions(prevGame.ID)
            if err != nil {
                return nil, fmt.Errorf("读取上一局BP记录失败: %w", err)
            }
            s.applyGlobalBPMemory(perms, actions, prevGame, blueTeamID, redTeamID)
        }
    }

    // 3. 元流之子五选一锁定（本方案新增；整场比赛累计，必须遍历全部历史局）
    if len(yuanliuIDs) > 0 && gameNumber > 1 {
        usedBlue, usedRed, err := s.collectYuanliuUsage(matchID, gameNumber, yuanliuIDs,
            blueTeamID, redTeamID, /* 固定身份见下 */)
        if err != nil {
            return nil, err
        }
        s.applyYuanliuLock(perms, yuanliuIDs, usedBlue, usedRed)
    }

    return NewBPEngineWithPerms(blueTeamID, redTeamID, perms, s.tournamentBanned, nil), nil
}
```

#### 步骤 2：`collectYuanliuUsage` — 跨局累计「跟队伍走」

⚠️ **关键陷阱**：历史记录里 `ban_pick_action.side` 存的是**颜色**，而每局的红蓝归属可能已换边
（§8.1 已经踩过一次这个坑）。因此必须沿用既有做法：**用该局自己的 `blue_team_id/red_team_id`
把颜色翻译成队伍身份**，再按"本局谁是蓝"翻译回颜色。

```go
// collectYuanliuUsage 返回本场比赛中「蓝队身份 / 红队身份」各自已 pick 过的元流英雄集合。
//
// 语义（与 applyGlobalBPMemory 完全一致）：限制跟队伍走，不跟颜色走。
// 每局用**该局**的 blue/red 归属把 action.side（颜色）翻译成队伍，最后按**本局**归属
// 落到 curBlue / curRed 两个桶里。
func (s *GameService) collectYuanliuUsage(
    matchID, currentGameNumber int, yuanliuIDs []int,
    curBlueTeamID, curRedTeamID int,
) (usedBlue, usedRed map[int]bool, err error) {
    usedBlue, usedRed = map[int]bool{}, map[int]bool{}
    inGroup := make(map[int]bool, len(yuanliuIDs))
    for _, id := range yuanliuIDs {
        inGroup[id] = true
    }

    games, err := s.gameRepo.ListGamesByMatch(matchID)
    if err != nil {
        return nil, nil, fmt.Errorf("读取比赛历史局失败: %w", err)
    }

    for _, g := range games {
        // 只统计"本局之前"的局（本局尚未开始，其记录必然为空；用 < 更直观且防脏数据）
        if g.GameNumber >= currentGameNumber {
            continue
        }
        actions, aerr := s.gameRepo.ListBPActions(g.ID)
        if aerr != nil {
            return nil, nil, fmt.Errorf("读取第%d局BP记录失败: %w", g.GameNumber, aerr)
        }
        for _, a := range actions {
            if a.ActionType != "pick" || !inGroup[a.HeroID] {
                continue // ban 不计入；非元流不计入
            }
            // 颜色 → 该局实际队伍 → 本局该队是蓝还是红
            var teamID int
            switch a.Side {
            case "blue":
                teamID = g.BlueTeamID
            case "red":
                teamID = g.RedTeamID
            default:
                continue
            }
            switch teamID {
            case curBlueTeamID:
                usedBlue[a.HeroID] = true
            case curRedTeamID:
                usedRed[a.HeroID] = true
            }
        }
    }
    return usedBlue, usedRed, nil
}
```

> **性能说明**：局数 ≤ 9（BO9 上限），每局动作 ≤ 20 条，总计 ≤ 180 次内存遍历 + 每局一次
> `ListBPActions`。这个量级远小于「每步 BP 都落库」的既有开销，**不需要缓存**。
> 若未来局数增大，可在 `Room` 上缓存累计集合，本方案不做（避免提前优化）。

#### 步骤 3：`applyYuanliuLock` — 只压 pick，绝不压 ban

```go
// applyYuanliuLock 把元流之子「五选一」锁定施加到权限表上。
//
// ⚠️ 语义（需求方确认，见方案 §1.2）：
//   - 只把 CanPick 压成 false；CanBan **一律保持原值**（队仍有 ban 五个元流的权力）
//   - 锁是"按队伍"的：A 队被锁不影响 B 队的五选一权力
//   - 只作用于"本队未用过的那几个"，已用过的由全局BP记忆另行处理
//   - 与其他规则叠加：不覆盖 NonePerm（赛事禁用需保持全 false）
func (s *GameService) applyYuanliuLock(
    perms map[int]*HeroPerm, groupIDs []int,
    usedBlue, usedRed map[int]bool,
) {
    lockedForBlue := YuanliuLocked(groupIDs, usedBlue)
    lockedForRed := YuanliuLocked(groupIDs, usedRed)

    for _, id := range groupIDs {
        p := perms[id]
        if p == nil {
            continue
        }
        // 赛事禁用（NonePerm）：全 false，不得被本规则"复活"任何位
        if !p.BlueCanBan && !p.BlueCanPick && !p.RedCanBan && !p.RedCanPick {
            continue
        }
        if lockedForBlue[id] {
            p.BlueCanPick = false // 蓝方已用过别的元流 → 本局不可再选
        }
        if lockedForRed[id] {
            p.RedCanPick = false
        }
        // 注意：BlueCanBan / RedCanBan 一律不动
    }
}
```

> ⚠️ **`perms` 里的指针是可变的**：`FullPerm()` 每次调用都返回**新指针**，
> 而 `NonePerm()` 也是新指针，因此就地修改 `p.BlueCanPick` 是安全的，不会串改其他英雄。
> 施工时必须**保持** `FullPerm()`/`NonePerm()` 每次返回新对象的既有实现（`bp_engine.go:248-255`），
> 不得改成共享单例 —— 否则 `applyYuanliuLock` 会污染全局。

### 8.1 ⚠️ 施工中发现的缺陷：方案对"局内锁定"的判断是错的（已修复）

**这是本次施工最重要的发现。方案 §2.1 的判断有误，真实缺陷被端到端实测捕获。**

**方案原判断（错误）**：

> "本集合只在每局开始时（`StartGame`）计算一次……本局内的 pick 不可能改变本局的锁定结果，
> 因此无需在 `ExecuteAction` 里动态重算，也不会出现'用完才变灰'的时序漏洞。"

**实际缺陷**：该判断**只对"跨局累计"成立，对"局内锁定"完全不成立**。

需求 1 的本义是**同一局之内**："一旦使用了元射，则其它四个元流都不能再选"。
但初版实现只在 `StartGame` 里派生权限表，而 `Engine.Permissions` 是**开局即固化的静态 map**
（`bp_engine.go` 中没有任何代码在 pick 后修改它）。后果：

```
第 1 局：蓝方 pick 元射 → 其余四个**仍可 pick**（规则完全失效）
第 2 局：才由 StartGame 的历史派生生效（此时才对）
```

即**"当局不锁、下局才锁"**，与需求 1 的文字直接冲突。

**证据（修复前的端到端输出）**：

```
【蓝方已 pick 元射（本局第5步）】
  英雄     蓝ban   蓝pick   红ban   红pick
  坦克     True   True    True   True     ← ❌ 应为 False
  法师     True   True    True   True     ← ❌ 应为 False
  ...
❌ A5【需求1】蓝方对其余四个元流不可pick  — 坦克、法师、刺客、辅助
❌ A8【需求3兜底】蓝方再 pick 坦克被后端拒绝  — HTTP 200 code=0   ← 竟然成功了
```

**修复方案：把"互斥组"下沉到 Engine，在 pick 后动态收紧权限。**

```go
// bp_engine.go — Engine 新增字段
ExclusiveGroups [][]int   // 互斥组（元流之子"五选一"）

// pick 成功后立即锁定该方对同组其余英雄的 pick 权
func (e *Engine) lockExclusiveGroupFor(side TeamSide, heroID int) {
    gi := e.GroupOf(heroID)
    if gi < 0 { return }
    for _, id := range e.ExclusiveGroups[gi] {
        if id == heroID { continue }
        p := e.Permissions[id]
        if p == nil { continue }
        // 不复活赛事禁用
        if !p.BlueCanBan && !p.BlueCanPick && !p.RedCanBan && !p.RedCanPick { continue }
        switch side {
        case Blue: p.BlueCanPick = false
        case Red:  p.RedCanPick  = false
        }
        // ⚠️ CanBan 一律不动
    }
}

// handlePick 末尾接线
e.lockExclusiveGroupFor(side, heroID)
```

`GameService.StartGame` 相应调整：

- 去掉 `gameNumber > 1` 的门槛（第 1 局历史为空、不产生跨局锁定，但**互斥组仍需注册**）；
- 新增 `engine.SetExclusiveGroups([][]int{yuanliuIDs})`。

**为什么方案当初会判断错**：把"锁定的输入"（历史 pick 集合）与"锁定的生效时机"混为一谈。
历史集合确实只在开局计算一次，但**本局的 pick 本身就是锁定的触发器** ——
这正是本规则区别于全局BP记忆的本质：后者依据"上一局"（开局即已知的常量），
前者必须在**本局内动态**响应。

**修复后同一位置的输出**（权限位与预期完全一致）：

```

```

### 9.1 问题与根因

**用户反馈原文**：

1. 前端问题：AG 本局选了元射，但是狼队后续还能 ban 元坦
2. AG 第一局用了元射，狼队第二把依旧能 ban 元坦
   （正常情况下是**所有元流狼队都不能 ban**）

**共同根因：需求 2 的后半句被误读。**

需求 2 原文：

> 基于第 1 点，若 A 队已使用元射，则 **B 队不用再 ban 其它四个元流**，
> 但 B 队依然可以进行元流五选一，**故而 A 队依然有 ban 五个元流的权力**

这句话包含**两个方向相反**的规则：

| 分句 | 方向 | 我的实现 |
|------|------|---------|
| "B 队**不用再 ban** 其它四个元流" | **剥夺 B 的 ban 权** | ❌ **漏做** |
| "故而 A 队**依然有 ban** 五个元流的权力" | **保护 A 的 ban 权** | ✅ 已做 |

初稿把第一句当成了第二句的**同义复述**（都理解成"A 的 ban 权不受影响"），
因此在 `applyYuanliuLock` / `lockExclusiveGroupFor` 中写下了
**"⚠️ BlueCanBan / RedCanBan 一律不动"** —— 只说对了 A 那一半，完全没处理 B。

**语义澄清**（经用户二次确认）：这里的"不用"是**授权缺失（不得）**，不是"可选但不必"。
A 用过之后，其余四个元流对 B 已无 pick 威胁，故 B 不需要、也不允许再 ban 它们。
而 A 自己的 ban 权是防守手段，不因己方已使用而剥夺。

**症状**（修复前实测）：

```
【AG(蓝) 已 pick 元射】
```

## 十、第五轮（实战反馈）：换边后"用过的那个"元流失去保护（已修复）

> 📅 完工日期：2026-10-14 ｜ ✅ 全部验收通过（58 个单测 + 真实 DB 端到端复现）
>
> 用户反馈：**狼队第一把选了元射，但是 AG 第三把依然能 ban 元射**
> （其它四个是不能 ban 的，说明其它四个没有 bug）

### 10.1 定位过程：直接读真实数据库

用户提示"看数据库里最新的一场比赛"。`match_record` 最新一条为 **id=60**：

```sql
SELECT id, game_number, blue_team_id, red_team_id, winner FROM game WHERE match_id=60;

 id  | game_number | blue | red | winner
 120 |      1      |  1   |  2  | blue     ← 狼队(1) 蓝
 121 |      2      |  2   |  1  | red      ← 换边，AG(2) 蓝
 122 |      3      |  1   |  2  | NULL     ← 换回，狼队(1) 蓝

SELECT g.game_number, a.step_order, a.action_type, a.side, a.hero_id, h.name
FROM ban_pick_action a JOIN game g ON g.id=a.game_id
LEFT JOIN hero h ON h.id=a.hero_id
WHERE g.match_id=60 AND a.hero_id IN (33,60,83,105,132) ORDER BY g.game_number, a.step_order;

 game | step | action | side | hero | name
   1  |   5  |  pick  | blue |  83  | 元流之子·射手   ← 狼队 pick 元射
   2  |   5  |  pick  | blue |  33  | 元流之子·坦克   ← AG   pick 元坦
   3  |   1  |  ban   | blue |  83  | 元流之子·射手   ← 狼队 ban 元射（❌ 非法）
```

**关键**：第 1 局用元射的队（id=1）与第 3 局 ban 元射的队是**同一支**（蓝方）。

### 10.2 根因：把"用过的那个"过度委托给了全局BP记忆

`YuanliuLocked` 当初**刻意把"用过的那个"排除在锁定集外**，注释理由是：

> "已用过的由全局BP记忆另行处理（自己选过不可再选），本函数不重复设置"

**这个委托在换边场景下失效了**，因为：

| 规则 | 回溯范围 |
|------|---------|
| 全局BP记忆 | **只看上一局**（`gameNumber - 1`） |
| 元流"本场累计" | **整场比赛全部历史局** |

第 3 局时，上一局是第 2 局 —— 而第 2 局狼队是**红方且没选元流**，
于是记忆规则里**根本没有元射这条记录**。结果元射：
既没被锁 pick、也没被剥夺对手 ban，成了唯一的漏网之鱼（其余四个因在 `lockedForBlue` 里而正常）。

**修复前的实测输出**（复现 match 60）：

```
英雄   蓝(狼队)ban  pick  | 红(AG)ban  pick
元坦     false      false  | false     false     ✅
元法     false      false  | false     false     ✅
元射     TRUE ✅?    TRUE ✅? | true      false     ❌ ← 漏网！
元刺     false      false  | false     false     ✅
元辅     false      false  | false     false     ✅
```

### 10.3 连带发现：同一个根因导致"可以重复 pick 自己用过的元流"

修 `ban` 时，新写的回归断言又暴露出**第二个同源缺陷**：
在第 3 局，狼队 `heroCan(Blue, Pick, 元射)` 返回 `available` ——
**它能把自己第 1 局已经用过的元射再选一次**，直接违反需求 1"本场比赛只能选一个"。

根因完全相同：pick 侧的约束也被委托给了只看上一局的记忆规则。

### 10.4 修复：让元流规则**自给自足**

不再委托记忆规则，改为独立对**整组五个**施加两条约束：

```go
// game_service.go — applyYuanliuLock
for _, su := range sides {          // 蓝、红 各自
    if len(su.used) == 0 { continue }   // 未用过 → 无任何限制
    for _, id := range groupIDs {       // ⚠️ 整组五个，含"用过的那个"
        p := perms[id]
        if p == nil { continue }
        if !p.BlueCanBan && !p.BlueCanPick && !p.RedCanBan && !p.RedCanPick { continue }
        su.oppBan(p)   // (a) 对手不可 ban（整组）
        su.ownPick(p)  // (b) 本队不可再 pick（整组，含用过的那个）
    }
}
```

局内路径 `lockExclusiveGroupFor` 同步调整 —— 关键是**两条规则作用范围不同**：

| 规则 | 作用范围 |
|------|---------|
| (a) 对手不可 ban | **整组五个**（含刚 pick 的那个） |
| (b) 本队不可再 pick | **其余四个**（刚 pick 的那个已被移出英雄池，无需再禁） |

> ✅ **用户口径原文**（最终确认）：
> "某个元流已被 A 队 pick 后，后续的局 A 队依旧可以 ban 所有元流，
> **B 队一个元流也不能 ban**（因为 A 队已经选不了元流了）。"
>
> 本条已用 `TestConfirm_OnlyAUsed` 逐位核对通过（见 §10.5）。

> 📌 设计教训：**当一条规则声称"本场累计"时，绝不能把它的任何一部分委托给
> 只看"上一局"的机制** —— 两者的时间窗口不同，换边会让差异暴露。
> 规则要么完全自给自足，要么显式做全量回溯。

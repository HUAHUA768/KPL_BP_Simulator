# BP 状态机开发难题复盘（面试素材）

> 用途：面试官问"这个项目你解决了什么难题"时的回答提纲。
> 原则：每个问题按 **背景 → 卡点 → 解决 → 面试一句话** 组织，先讲结论再补细节。
> 总览：**共 6 个问题**，按面试含金量排序。

---

## 问题 1：BP 流程规则本身是"易错且必须精确"的——需求迭代中多次改错

**背景**：BP（Ban/Pick）是王者荣耀比赛的选角流程，规则细节决定整个状态机的骨架。项目开始时我对真实 KPL 规则只有一个模糊印象。

**卡点**：
- 最初按"三个循环"设计（3×? 步），被指出错误。
- 之后又改成"两轮 20 步"，但第一轮和第二轮的**先后手、ban/pick 交错顺序**极易搞混（谁先 ban、谁先 pick、一轮里 4ban6pick 还是 6ban4pick）。
- README 和设计文档各自维护过一份规则，一度出现"步骤表"和"汇总表"数字对不上的不一致。

**解决**：
1. 和需求方（用户）逐轮核对，最终敲定唯一的 **20 步对照表**（见 实现思路.md 四、BP 规则详解），以该表为**唯一事实来源**。
2. 把规则直接写成代码常量 + 纯函数 `getTurnInfo(turn)`，让**步骤表存在于代码里**，而不是散落在文档里。
3. 用 `TestGetTurnInfo` 对 20 步逐条断言（哪一步、谁、什么动作、第几次），**测试即规则文档**——以后再改规则，测试会先告诉我们对不对。

**面试一句话**：业务规则越"理所当然"越要警惕，我把 BP 20 步流程收敛成唯一权威表格，并用"常量 + 纯函数 + 逐条单测"把它固化在代码里，消除了文档与实现不一致的隐患。

## 问题 2：Go 的 iota 常量陷阱——一步写错，20 步全错位（真实 bug）

**背景**：用 `iota` 定义 20 个步骤常量 `Turn1~Turn20`，第一循环用 `BPTurn = iota + 1` 起始。

**卡点**：第二循环的起始常量我写成了 `Turn11_RedBan3 BPTurn = iota + 11`。看似"从 11 开始"，但 **iota 是常量块内的累积下标**——写到第 11 个常量时 `iota` 已经等于 10，于是 `10 + 11 = 21`，导致 Turn11~Turn20 全部错位成 21~30，`getTurnInfo` 匹配不到任何 case，轮次判定全部落到 `Round 0（未知）`。

**解决**：跑单测时 `TestEngine_Round1_Flow`、`TestEngine_Round2_Flow` 同时爆出"轮次=0"和"turn=21"，顺着失败快速定位到常量定义，改为让第二循环**继承第一循环的 `iota + 1` 表达式**（去掉显式偏移），20 步常量值与步骤表完全对齐，全部测试转绿。

**面试一句话**：这是我印象最深的一个 Go 细节——`iota` 是常量块的累计下标而非"当前行的值"，一个"看着对"的偏移写法能让整张步骤表静默错位；而恰好因为我有逐步骤的单元测试，bug 一落地就被机器抓出来了，而不是等联调时靠人眼发现。

## 问题 3：模型演进——从"共享英雄池"到"按队伍区分权限的四布尔模型"

**背景**：最初 `HeroPool map[int]bool` 两队共享，任何被 ban/pick 的英雄直接从池中移除，天然保证"对手用过的英雄不能再被 ban"。这个模型简单且自洽。

**卡点**：需求提出**全局BP记忆**规则——上局**红方**选了英雄 x，下局 x 要变成"**蓝方**可选但不可ban、**红方**可ban但不可选"。这是一个**不对称权限**：同一个英雄，对蓝队是可 pick、不可 ban；对红队是可 ban、不可 pick。共享池（池内有=双方都能用，池外=双方都不能用）**根本表达不了"一方能用、一方不能用"**。

**解决**：
- 引入 `HeroPerm`：每个英雄 4 个独立布尔 `BlueCanBan / BlueCanPick / RedCanBan / RedCanPick`。
- Engine 持有 `Permissions map[int]*HeroPerm`；`heroCan(side, action, heroID)` 按"视角"判断可用性。
- 保留 `NewBPEngine`（共享池兼容封装，自动转 FullPerm 全权限），新增 `NewBPEngineWithPerms` 支持不对称初始权限——**旧的调用方和测试一行不用改**。
- 新增 `TestHeroCanPerms`、`TestGlobalBPMemory_*` 专门验证不对称规则。
- 跨局"恢复原状"由对局编排器 `GameService` 负责：每局开始时读取上一局 pick 记录，派生下局权限，创建全新的 Engine（Engine 生命周期 = 一局，从不自我重置）。

**面试一句话**：需求从一个"必须对称"的假设变成"可不对称"时，我没有在共享池上打补丁，而是识别出模型表达能力不够，升级为按队伍区分的权限模型，同时用新构造函数兼容旧接口，把改动隔离在新增能力上。

## 问题 4：报错信息的语义粒度——从"英雄不可用"到可解析的错误契约

**背景**：第一版 `handleBan/handlePick` 失败时统一返回"英雄不在可用池中"，前端只能显示一句话，用户没法区分原因。

**卡点**：同样一个"不能 ban"，背后可能是 **4 种完全不同的原因**：赛事禁用（雅典娜，永远不能出现在界面）、已被自己或对手 ban、已被对手 pick、英雄 ID 不存在。前端需要根据原因决定 UI 表现（禁用区置灰 / 阵容区置灰 / 直接不显示），模糊错误无法驱动。

**解决**：
- 引入 `HeroStatus` 枚举（7 种状态），`heroStatus(heroID)` 按固定判定顺序：赛事禁用 → 被ban → 被pick → 池中可用 → 未知。
- 引入 `heroCan(side, action, heroID)` 视角级判断（覆盖不对称权限场景）。
- `heroUnavailableError` 按状态生成带原因的报错信息；在 docs/API.md 里和后端约定 **40001~40008 错误码契约**。
- 补充全局BP新增的状态 `HeroRestrictedByRule`，并同步更新 README 的前端渲染规则表。

**面试一句话**：任何被拒绝的操作都要能告诉调用方"为什么"，我通过状态枚举 + 判定顺序 + 错误码契约，把一句模糊的"不可用"细化为 8 类可编程、前端可直接驱动 UI 的错误语义，联调成本大幅下降。

## 问题 5：校验逻辑的依赖注入——状态机要与具体校验解耦

**背景**：状态机只管"流程对不对"（顺序、动作类型、哪一方），但"能不能 ban 这个英雄"涉及具体业务校验（英雄是否存在、是否赛事禁用等），如果写死在 Engine 里，状态机就没法单独测试。

**卡点**：如何让 Engine 既完成流程编排、又能被任意校验规则复用，同时不引入 MySQL/Redis 等外部依赖？

**解决**：
- 定义 `Validator` 接口（`ValidateBan / ValidatePick`），Engine 构造时注入；测试里用 `mockValidator` 只放行 1~100 的英雄，完全隔离外部资源。
- 提供 `NoopValidator` 兜底（nil 时默认全放行），GameService 编排场景传 nil 也不会 panic。
- 由此 Engine 的 14+ 个测试全部在毫秒级内存环境中跑完，无任何 IO。

**面试一句话**：状态机是一个纯内存对象，我把"业务校验"抽象成注入接口，让引擎可以脱离数据库独立测试——这是依赖倒置在真实业务里的应用，测试速度和覆盖度都上去了。

## 问题 6：测试先行的工作流——先验证状态机，再实现上层编排

**背景**：实现 `GameService`（对局编排器）之前，用户提出"先测试 BP 状态机"，理由是状态机是整个项目的核心，如果它错了，上面所有层都会跟着错。

**卡点**：直接跳到 orchestration 层的话，一旦状态机有 bug，排查时等于在两层之间来回猜。

**解决**：
1. **先用测试把状态机钉死**：20 步顺序表、完整跑完一局、两轮流程边界、ban/pick 逻辑、非法动作、重复 ban、赛事禁用、不能 ban 对手已 pick 的英雄、HeroStatus 全状态、全局BP不对称权限——共 22 个测试。
2. 全部通过后，才动手写 `GameService`：加载英雄池 → 派生权限 → 建新 Engine → 落库 20 步操作记录，配套内存版 mock repo 单测（6 个测试）。
3. 实际收益：**问题 2 的 iota bug 就是被这套测试当场抓出来的**——"先测核心"这个流程直接避免了一个隐蔽 bug 流入上层。

**面试一句话**：我按"先测试底层核心、再测试上层编排"的顺序推进——状态机 22 个测试、编排器 6 个测试全部通过后才继续写 handler/websocket，事实证明这个顺序让一个 iota 导致的静默 bug 在第一时间暴露，而不是流到联调阶段。

## 附录：开发环境踩坑（可讲，但不算"难题"）

- **无系统 Go 环境**：服务器/工作目录只读，把 Go 工具链装进项目 `.tools/`，通过 PATH/GOCACHE/GOPATH 环境变量隔离，不污染系统。
- **依赖下载慢/卡住**：配置 `GOPROXY=https://goproxy.cn,direct` 走国内镜像，构建从超时到秒级完成。
- **匿名结构体语法**：测试里写 `[]struct{ turn BPTurn, side TeamSide }` 是 Go 非法语法（内联结构体字段不能逗号分隔），改为多行声明。

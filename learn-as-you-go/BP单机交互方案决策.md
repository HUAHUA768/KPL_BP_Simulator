# BP 单机交互方案决策记录（讨论稿）

> 状态：**已定稿，待实施**
> 范围：前端 BP 房间交互模型 + 通信通道收敛；后端引擎不动。
> 关联代码：`frontend/src/pages/BPRoom.tsx`、`frontend/src/components/BanPickBoard.tsx`、`frontend/src/hooks/useWebSocket.ts`、`backend/internal/handler/room_handler.go`

---

## 一、问题背景

当前前端进入 BP 房间时，"操作方"被写死为 URL 参数：

```
/room/:id?side=blue        // BPRoom.tsx: mySide = searchParams.get('side') || 'blue'
```

`BanPickBoard` 用它做权限门控：

```ts
const isMyTurnNow = side === mySide && (action === 'ban' || action === 'pick')
```

第 1 步（蓝方 ban）可以正常操作；引擎推进到第 2 步（红方 ban）后，`mySide` 仍是 `blue`，所有点击被静默吞掉，界面停在"👀 等待对方操作"——**单机场景下这个"对方"永远不存在，流程卡死**。

关键观察：后端 BP 引擎（`bp_engine.go`）是严格按 20 步状态机推进的纯服务端逻辑，`ExecuteAction` 只校验动作类型和英雄合法性，**从不校验"请求者是谁"**。也就是说，回合归属本来就是引擎的唯一事实来源，前端的 `mySide` 门控是多余的自设锁。

---

## 二、候选方案对比

| 维度 | 方案 A：双端口（两窗口各持一方） | 方案 B：同屏分两半 | 方案 C：一人分饰两角 ✅ |
|------|--------------------------------|--------------------|------------------------|
| 本质 | 两个浏览器窗口各连一个 WS，分别操作蓝/红 | 一个页面渲染两套操作区 | 单页面，操作角色跟随引擎回合切换 |
| 改动量 | 最大：跨窗口状态同步、主持人选举、REST+WS 竞态全要处理 | 中：Board 大改，且逻辑上仍是 C（两边都是同一人操作） | **最小：解除 mySide 门控 + 视觉强化即可** |
| 演示风险 | 面试现场开两窗口容易翻车 | 两套英雄池布局别扭 | 单页面，操作路径最短 |
| 与目标匹配 | 为"未来双人"过度投资 | 同左 | ✅ 完全匹配"实习面试作品、不做多人拓展"的定位 |

**结论：采用方案 C。** 项目定位是单机 BP 模拟器（自己和自己下棋），双人模式只在架构上预留接口，不投入实现。

## 三、定稿的四个决策点

### 3.1 换边提示强度：主题色切换 + 槽位闪烁动画

- **主题色切换**：当前回合方决定页面强调色（蓝方回合 → 蓝色系，红方回合 → 红色系），横幅文字升级为醒目状态条，明确显示"当前扮演：🔴 红方 · 禁用"。
- **槽位闪烁（核心动画）**：
  - 轮到当前方操作时，**该方接下来将被填充的空槽位闪烁**：ban 阶段蓝红严格交替、每步只闪 1 个空位；pick 阶段存在同方连续两步（红 pick1→pick2、蓝 pick2→pick3、蓝 pick4→pick5），对应的**两个空位同时闪**。
  - 动作完成后，英雄"落座"，槽位**停止闪烁恢复静态**——安安静静待在 ban 位上。
  - pick 回合同理：闪烁的是当前方的空 pick 槽位。
  - 闪烁只作用于**当前操作方的空槽位**，英雄池不加呼吸/描边动画（保持界面干净，控制实现成本）。

### 3.2 架构预留双人扩展，但不影响单机业务

引入显式的**交互模式**概念（如 `mode=solo | dual`，默认 `solo`）：

- `solo` 模式：有效操作方 = 引擎返回的 `state.side`（谁回合谁就是"我"），门控恒通过。
- `dual` 模式：沿用现有语义，有效操作方 = URL 传入的 `side`，非本方回合只读等待。

门控逻辑收敛为一处纯函数（如 `resolveActor(state, mode, urlSide)`），未来真做双人时只需补 `dual` 模式的接入层，**单机主流程零改动**。

### 3.3 AI 辅助代打：本期不做

不引入"AI 替对方完成一步"等功能。留作后续可讲的扩展方向（面试话术见面试版文档），不进本期范围。

### 3.4 REST 与 WS 双通道广播：收敛为单向数据流

现状是**双写**：`handleBanHero` 先调 REST `POST /rooms/:id/ban` 拿回新状态写入 store，随后又 `wsBan(hero.id)` 把同一动作再发一遍，后端还会向房间内所有客户端（包括发起者自己）广播更新——一次点击触发多次状态更新，存在竞态与重复应用风险。

**目标形态（命令/事件分离）**：

```
用户点击 ──► REST 提交动作（唯一的写路径）
                │
                ▼
        后端引擎执行 + 持久化
                │
                ├──► HTTP 响应：权威状态（发起者据此立即更新 UI）
                │
                └──► WS 广播：状态快照（供其他观察者；solo 模式下发起者可忽略或幂等合并）
```

具体规则：

1. 前端**删除** `wsBan` / `wsPick` 发送调用——WS 降级为纯下行推送通道（保留连接与订阅，价值在讲架构时可说"通道能力已具备，只是单机不需要上行"）。
2. 状态更新以 REST 响应为唯一即时来源；WS 消息按"快照 + 版本号/步序"做**幂等合并**（旧快照直接丢弃），保证任何一条消息丢失或乱序都不会污染本地状态。
3. 后端 `broadcastUpdate` 维持"推完整状态快照"的风格（现在已是如此），避免增量 diff 带来的合并复杂度。

## 四、改动清单（实施时对照）

### 前端

| 文件 | 改动 |
|------|------|
| `pages/BPRoom.tsx` | 读取 `mode` 参数（默认 solo）；删除 `wsBan/wsPick` 调用；顶栏"你: X方"改为"当前扮演: X方"并随回合切换 |
| `components/BanPickBoard.tsx` | 门控改用 `resolveActor`；空槽位闪烁动画（CSS keyframes，按 `side/action/currentTurn` 计算哪些槽位该闪）；主题色 class 随回合方切换 |
| `hooks/useWebSocket.ts` | 移除上行发送 API（或标记 deprecated）；消息处理加幂等合并（比较 stepOrder/版本） |
| `store/bpStore.ts` | 增加 `mode`、必要时增加快照序号字段用于幂等判断 |
| 新增 `utils/actor.ts`（或并入 store） | `resolveActor(state, mode, urlSide): 'blue' \| 'red'` 纯函数，双人扩展的唯一接缝 |

### 后端

**零必要改动。** 引擎本就无请求者身份校验，天然兼容 solo 模式。可选小项：HTTP 响应与 WS 广播的状态体里带上统一的 `stepOrder`（若尚无），供前端幂等合并使用。

### 明确不做

- 跨窗口同步 / BroadcastChannel / SharedWorker
- AI 代打、防误触确认弹窗
- 英雄池整体呼吸动画

## 五、验收标准

1. 从第 1 步点到第 20 步全程无卡顿，无需修改 URL。
2. 每个 ban/pick 回合：当前方对应空槽位闪烁；动作完成后槽位静止、动画停止。
3. 页面主题色（横幅、高亮、边框强调）随蓝/红回合切换，肉眼可辨"现在扮演谁"。
4. 一次点击只产生一次状态更新（Network 面板确认：1 个 REST 请求；WS 仅有下行消息，无上行帧）。
5. 带 `?mode=dual&side=blue` 访问时，红方回合不可操作、显示等待——证明扩展接缝存在且未污染 solo 主流程。

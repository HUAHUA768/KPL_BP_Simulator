# BP 交互设计与通信收敛（面试素材）

> 用途：面试官问"这个项目前端和实时通信部分你做了什么设计 / 遇到过什么问题"时的回答提纲。
> 原则：先讲结论，再给一层细节；每个点都留一个"追问钩子"。
> 姊妹篇：《BP状态机开发难题复盘.md》（引擎侧），本篇是交互与通信侧。

---

## 电梯陈述（30 秒版本）

> "这是个单机 BP 模拟器，但后端我按真实对战架构做的：20 步状态机 + WebSocket 房间推送。前端最初按双人对战假设写了'本方回合才可操作'的门控，导致蓝方操作完、轮到红方时流程卡死——因为单机场景里'对方'不存在。我的解法不是简单删掉检查，而是把**回合归属收敛为服务端引擎的唯一事实来源**，前端引入 solo/dual 交互模式抽象：solo 下操作角色跟随引擎回合切换，dual 保留双人语义作为扩展接缝。同时把原来 REST 提交 + WS 回显的**双写通道收敛为命令/事件分离**的单向数据流，消除了重复广播竞态。"

## 问题 1：单机模式下 BP 流程卡在换边

**背景**：KPL BP 共 20 步、蓝红交替（ban 阶段严格交替；pick 阶段存在同方连续两步，如红 pick1→pick2、蓝 pick2→pick3、蓝 pick4→pick5），全部由 Go 后端状态机推进。前端进入房间时通过 `?side=blue` 声明"我是谁"，非本方回合禁用点击。

**卡点**：项目定位是单机模拟器（一人分饰两角），但交互模型是双人的。第 2 步轮到红方时，页面显示"等待对方操作"，而对方永远不会出现——**不是 bug，是交互模型和产品定位错配**。当时有三个候选方案：开两个端口各持一方、同屏分两半、单页角色随回合切换。

**解决**：选了第三种，理由有二：
1. **最小正确改动**——后端 `ExecuteAction` 本来就不校验请求者身份，回合归属在引擎里是唯一事实来源，前端的 `mySide` 门控是自设锁，开锁即可；
2. **可解释性**——演示时单页面路径最短，面试现场不多开窗口就不少一分翻车风险。

落地成体验设计：主题色随蓝/红回合整体切换；当前方的空 ban/pick 槽位闪烁引导，动作完成后英雄"落座"、动画停止——用视觉语言告诉用户"现在你在扮演谁"，替代文字说明。

**面试一句话**："我没有把它当 bug 修，而是识别出这是交互模型与产品定位的错配，然后用'服务端单一事实来源 + 前端模式抽象'来修，顺带设计了换边动画。"

**追问钩子**：为什么不做双窗口？→ 见问题 2。要不要防误触/AI 代打？→ 主动说本期不做，是范围控制（体现取舍）。

## 问题 2：预留双人扩展，但不为它付实现成本

**背景**：完全删掉回合门控最省事，但会把"未来支持双人"的路堵死，也显得设计粗暴。

**卡点**：扩展性设计的常见陷阱是**提前实现**——为不存在的用户需求引入跨窗口同步、连接选举这类复杂度。

**解决**：把"谁是有效操作方"收敛成一个纯函数 `resolveActor(state, mode, urlSide)`：
- `mode=solo`（默认）：返回引擎的当前回合方 → 主流程零门控；
- `mode=dual`：返回 URL 声明方 → 保留原有等待语义。

真做双人时只需要补接入层（第二客户端如何获得身份），业务逻辑不动。**接口先行、实现后置**，扩展成本被压缩到一个函数的分支里。

**面试一句话**："我用一个模式参数把扩展点显式化了——架构上支持双人，代码里只多了一个纯函数分支，没有为假想需求付任何运行时复杂度。"

**追问钩子**：如果真要双人，下一步改什么？→ 答：WS 上行恢复为动作命令、服务端加连接与身份的绑定校验、断线重连拉全量快照。这些都是现成骨架能承接的。

## 问题 3：REST + WebSocket 双写通道的竞态

**背景**：原实现一次点击走两条路——先 `POST /rooms/:id/ban` 拿响应更新 store，又通过 WS 把同一动作再发一遍；后端执行后还向房间内所有客户端（包括发起者）广播新状态。

**卡点**：同一个动作有两次提交路径、状态更新有多个来源，到达顺序不确定；重复应用/旧覆盖新的风险都在，且随着全局 BP 记忆这类跨局状态叠加会越来越难推理。

**解决**：收敛为**命令/事件分离**的单向数据流：
- **写路径唯一**：动作只经 REST 提交，HTTP 响应即权威状态，发起者据此立即渲染；
- **WS 降级为纯下行**：只推完整状态快照，供观察者通道使用（solo 模式下前端甚至不发上行帧）；
- **幂等合并**：快照携带步序/版本，本地比较后丢弃过期消息，乱序与丢失都不污染状态。

选"推完整快照"而不是"推增量 diff"，是因为 20 步 × 百余英雄的状态体量很小，快照让任意时刻的合并逻辑退化为一次赋值，工程上更稳。

**面试一句话**："我把双写通道改成 CQRS 味儿的单向数据流：命令走 HTTP，状态走 WS 快照 + 版本号幂等合并，从根上消灭了竞态，而且这套机制天然支持断线重连补齐。"

**追问钩子**：为什么不干脆全走 WS？→ 可以讲 HTTP 的请求-响应语义更适合承担"动作是否合法"的同步反馈（40001~40007 错误契约直接映射到 UI），WS 负责异步扩散，职责清晰。

## 通用应答弹药

- **"这项目最大难点？"** → 引擎侧是 20 步状态机 + 全局 BP 记忆的不对称权限（见姊妹篇）；系统侧是这次通信模型的收敛：从双写到命令/事件分离。
- **"前端你会什么？"** → 不必深谈框架，聚焦三点：状态管理（zustand 单一 store）、派生状态纯函数化（resolveActor / heroStatus 前后端同构契约）、动画只用 CSS keyframes 驱动避免 JS 计时器。
- **"如果给你两周继续做？"** → 优先级：① dual 模式接入层（真双人）；② AI 代打（规则启发式即可，不需要模型）；③ 对局复盘时间轴回放（动作日志已持久化，回放只是重放状态机）。
